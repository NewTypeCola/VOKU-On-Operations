## 실제 운영 검증

실사용자를 조회하지 않고 기존 **test 활동 28건**만 대상으로 확인했다. 원본 경로·회원정보를 검증 산출물에 저장하지 않았다.

1. 전용 역할로 목적·기간을 기록하고 커밋한 뒤 별도 호출로 결과를 받았다. 제한된 식별값 포함 여부 false, test 대상만 포함 true, `canonicalEvents` SHA-256 일치 true.
2. 감사 기록에 접속 주체 `postgres`, 사용 역할 `voku_usage_reader`, 목적 `data_quality`, 범위·건수·체크섬이 저장됐다.
3. 같은 트랜잭션에서 결과를 읽으려는 시도를 실제 DB가 거부했다.
4. 결과를 읽은 트랜잭션을 롤백해도 확정된 요청 1건과 이전 전달 기록 1건이 유지됐다. 전달 테이블 자체는 읽기 롤백의 영향을 받을 수 있다.
5. Supabase PostgreSQL 로그에서 `voku_analysis.read_result`의 `RAISE LOG` 발생을 확인했다. 이 외부 로그의 보관은 Supabase 설정을 따른다.
6. 분석 역할의 회원·원시 이벤트 SELECT 및 감사 기록 UPDATE가 실제로 거부됐다. anon/authenticated/service_role의 분석 실행 권한도 없다.
7. 기존 커뮤니티 함수 55개의 정의 해시가 적용 전후 동일했다: `95f5b841ece5a32b94b22d1ed1b553b6`.
8. 운영 HTTP 검사에서 test 이벤트 2건 수신, 같은 이벤트 중복 2건 처리, 다른 Origin 403, 비로그인 통계 401, 수집 키 없는 우회 401, 기존 공개 게시판 200을 확인했다.
9. `voku-analysis-retention` cron의 활성 상태와 15분 주기를 확인했다. 향후 예약 실행까지 관측한 것은 아니다.

보안 진단의 새 WARN/ERROR는 없다. `voku_analysis.results`의 RLS 정책 없음 INFO는 직접 접근을 허용하지 않고 검증 함수만 사용하는 의도된 구성이다. [공식 진단 설명](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy). 기존 커뮤니티·Auth 경고는 이전 검증 문서에 기록되어 있다.

## 사용 범위

현재 기존 DB 관리자 `postgres`만 새 그룹에 속한다. 운영자 웹 로그인으로 개별 경로를 볼 수 없으며 별도 계정이나 공유 비밀번호를 발급하지 않았다. 여러 사람이 분석한다면 개인별 전용 DB 로그인에 제한된 그룹만 부여해야 접속 주체를 사람별로 구분할 수 있다. DB 소유자의 관리 권한까지 제한하거나 모든 관리자 SQL을 감사하는 체계는 아니다.
