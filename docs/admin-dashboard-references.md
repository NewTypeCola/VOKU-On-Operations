# 한국 커뮤니티 운영 대시보드 사례 검토

조사일: 2026-10-12. 공식 사이트·공개 소스·관리자 데모를 기준으로 비교했습니다. 이 문서의 화면 구성은 제안이며, 완성된 대시보드나 구현 완료 목록이 아닙니다.

## 결론

VOKU에는 **라이믹스의 콘텐츠 관리 분류를 기본으로, 그누보드5의 검색·표 중심 작업 방식과 이윰의 기능별 관리자 권한 구성을 참고하는 방향**을 권장합니다. 그누보드7은 사이드바와 요약 영역의 시각적 참고로 활용할 수 있습니다.

선택된 “화면 구성을 참고해 VOKU 전용으로 구현” 방향은 유지할 수 있습니다. 아래 제품의 전체 시스템을 가져오면 각 제품의 회원·게시판·인증·데이터베이스 구조를 기존 Supabase에 맞추는 별도 작업이 필요합니다.

### 라이믹스

[공식 데모](https://demo.rhymix.org/)에서 안내하는 공개 체험 계정은 `test / test12`입니다. 로그인 후 프로필의 관리 메뉴로 들어갈 수 있습니다. [관리자 바로가기](https://demo.rhymix.org/index.php?module=admin), [공식 소스](https://github.com/rhymix/rhymix).

첫 화면은 방문 통계와 새 글·최근 댓글을 함께 보여줍니다. 콘텐츠 메뉴는 게시판·문서·댓글·파일·휴지통 등으로 나뉩니다. 문서 목록에서는 전체·공개·비밀·임시·신고 목록을 구분하고, 게시판 및 제목·내용·작성자 등의 검색 조건을 제공합니다. 휴지통·삭제·이동·복사 제어가 보이는 것까지 확인했으며, 처리 동작을 실행하지는 않았습니다.

글·댓글·회원 관리를 별도 화면으로 분리하는 정보 구조가 VOKU의 운영 업무와 가장 가깝다는 판단입니다. 화면의 작은 글자나 오래된 시각 요소까지 그대로 따를 필요는 없습니다.

### 그누보드5

[공식 관리자 데모](https://demo.sir.kr/gnuboard5/adm/), [관리자 메인 매뉴얼](https://sir.kr/manuals/g5/3), [관리자 소스](https://github.com/gnuboard/gnuboard5/tree/master/adm).

실제 데모 첫 화면에서 신규 가입 회원과 최근 포인트 내역의 표, 회원관리·게시판관리 메뉴를 확인했습니다. 공식 매뉴얼에는 최근 게시물도 설명되어 있으나, 현재 접속한 데모 메인에는 해당 영역이 나타나지 않았습니다. 데모와 매뉴얼을 같은 화면으로 취급하지 않았습니다.

VOKU에는 포인트·쇼핑몰 지표보다 게시판·상태·기간·작성자 검색, 선택 처리, 처리 결과 확인 같은 목록 작업 방식을 참고하는 것이 유용합니다.

### 이윰빌더

[공식 소개](https://eyoom.net/page/eb4_introduction), [관리자 메인 화면](https://eyoom.net/page/eb4_manual_02_3), [다중관리자 설정 화면](https://eyoom.net/page/eb4_manual_03_3).

공식 매뉴얼에서 관리자 메인, 밝은/어두운 화면, 자주 사용하는 메뉴 등록, 기능별 관리자 메뉴 부여 방식을 볼 수 있습니다. 특히 회원 검색 후 담당 기능을 선택하는 권한 설정 흐름이 이번 요구와 관련이 큽니다.

다만 이윰의 다중관리자는 기존 회원에게 관리자 기능을 부여하는 모델입니다. **VOKU에서 요구한 별도 운영자 계정과 동일한 설계는 아닙니다.** 권한 선택 화면의 표현 방식을 참고하고 실제 인증·인가 구조는 별도로 구현해야 합니다.

공식 사이트가 연결하는 관리자 데모는 이번 조사에서 로그인 화면까지만 열렸고 공개 로그인 정보를 확인하지 못했습니다. 따라서 체험용 로그인 성공을 보장하는 링크로 소개하지 않습니다.

### 그누보드7을 그대로 가져오는 방안

[공식 데모](https://g7.gnuboard.com/admin), [공식 저장소](https://github.com/gnuboard/g7). 데모 로그인 화면에는 공개 체험 계정과 자동 입력 버튼이 제공됩니다.

조사한 소스 기준점은 `dbe88420c3219f42db1ac16a7e6bb17a438e144d`입니다. README의 제품 버전은 7.1.0이며, PHP/Laravel 백엔드와 React 프런트엔드로 구성됩니다. [관리자 템플릿](https://github.com/gnuboard/g7/blob/dbe88420c3219f42db1ac16a7e6bb17a438e144d/templates/_bundled/sirsoft-admin_basic/layouts/admin_dashboard.g7.html)은 G7 API와 템플릿 런타임을 사용합니다. [DashboardService](https://github.com/gnuboard/g7/blob/dbe88420c3219f42db1ac16a7e6bb17a438e144d/app/Services/DashboardService.php)도 G7의 회원·활동·모듈·플러그인 저장 구조에 의존합니다.

따라서 G7 전체 도입보다 VOKU 데이터와 권한에 맞춘 전용 화면 구현을 권장합니다. 저장소에 PostgreSQL 연결 설정도 있으므로 “PostgreSQL을 전혀 사용할 수 없어서 불가”가 이유는 아닙니다. 핵심은 기존 Supabase의 테이블·Auth·RLS와 G7의 계약이 서로 다르다는 점입니다.

### 추가 화면 사례: RX 대시보드

[제작자 소개와 공개 화면](https://rhymix.org/pds/1948289). 기본 라이믹스 관리자와 별개인 제3자 모듈이며, 작성자는 AI로 작성했고 사람이 검토한 부분이 적다고 명시합니다. 댓글에는 설치·제거 및 동작 관련 논의와 수정 내용이 있습니다. 현재 결함 여부를 단정할 근거로 삼지 않고, 추가 화면 참고용으로만 분류합니다.

## VOKU 적용 제안

운영자는 **로그인 → 처리할 일 확인 → 목록에서 대상 선택 → 원문과 신고·처리 이력 확인 → 사유를 기록해 처리 → 목록 복귀** 순서로 업무를 마칩니다. 처리 전의 검색 조건과 페이지를 유지하면 다음 대상을 이어서 검토할 수 있습니다.

데스크톱 화면은 왼쪽에 고정 메뉴, 중앙에 검색·상태 필터·목록, 항목 선택 시 오른쪽에 상세 내용을 배치하는 안을 제안합니다. 한 화면에서 원문과 처리 사유를 함께 볼 수 있도록 읽기 영역을 충분히 확보합니다.

| 제안 메뉴 | 주된 업무 | 참고 사례 |
| --- | --- | --- |
| 운영 현황 | 미처리 신고, 최근 처리, 새 글·회원 요약 | 라이믹스의 요약→목록 연결 |
| 글·댓글 | 게시판·상태·기간·작성자 검색, 공지와 노출 상태 관리 | 라이믹스·그누보드5 |
| 신고 처리 | 대상 원문 확인, 사유 기록, 처리 상태 확인 | 라이믹스 신고 목록 + VOKU 기존 업무 |
| 회원 | 상태 확인과 필요한 운영 조치 | 그누보드5의 표 중심 관리 |
| 운영자·권한 | 별도 운영자 계정과 담당 기능 관리 | 이윰의 기능별 권한 표현 |
| 처리 기록 | 누가 언제 무엇을 왜 처리했는지 조회 | VOKU 기존 기록 체계 확장 |

이는 제안 메뉴이며 전부 구현된 기능을 뜻하지 않습니다. 첨부파일·아카이브·배너 편집은 실제 데이터 연결 범위를 확인하여 별도로 정해야 합니다. 기존 웹앱의 배너와 아카이브 목록 일부는 정적 파일을 읽고 있으므로, 운영 화면만 추가한다고 웹앱에 자동 반영되지는 않습니다.

## 기존 시스템에서 확인한 권한 경계

이번 세션에서 VOKU 소스와 공유 Supabase의 함수·스키마를 읽기 전용으로 확인했습니다.

- 웹앱 관리자 화면에는 글·공지, 신고, 처리 기록 탭이 있습니다. 서버의 기존 관리자 함수는 회원 관리 관련 기능도 갖고 있으므로 화면에 없는 기능을 권한이 없는 기능으로 간주하면 안 됩니다.
- 기존 게시판 관리자 판별은 커뮤니티 회원의 `admin`·`moderator` 역할을 사용합니다. 운영자 권한을 이 역할에 덧붙이는 방식은 요구한 권한 분리에 적합하지 않습니다.
- 가입 시 커뮤니티 프로필과 회원 행을 만드는 Auth 트리거가 있습니다. 운영자 전용 계정을 만들 때 커뮤니티 회원 생성과의 관계도 함께 처리해야 합니다.

제안은 같은 Supabase 프로젝트 안에서 운영자 전용 계정과 별도 권한 테이블·서버 권한 검사를 두는 방식입니다. 화면이나 브라우저 세션만 분리해서는 충분하지 않습니다. 같은 Auth 프로젝트를 사용하는 만큼 완전히 독립된 인증 시스템이라고 표현하지 않습니다. [Supabase RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security), [역할 기반 권한 문서](https://supabase.com/docs/guides/api/custom-claims-and-role-based-access-control-rbac).

기존 게시판 관리자의 권한은 보존하고, 새 운영자 권한으로 자동 승격하지 않는 것이 요구사항입니다. 실제 역할표·최초 계정 등록·마이그레이션은 구현 단계에서 다룹니다.
