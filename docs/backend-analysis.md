# 백엔드 이용 경로 분석과 조회 이력

기준일: 2026-10-15. 대시보드·CSV·외부 제출 보고서는 기존 집계 전용 구조를 유지한다. 개인별 경로의 웹 화면이나 공개 RPC를 추가하지 않는다. 이 문서는 DB 연결을 사용하는 제한된 내부 분석 절차다.

## 권한

- `voku_usage_reader`: `voku_analysis.prepare`, `read_result`, `my_requests`만 실행한다. 원시 이벤트·브라우저 식별값·해시 비밀값·회원·글·댓글·운영 테이블을 직접 조회하거나 수정할 수 없다. 감사 기록과 임시 결과 테이블도 직접 접근하지 못한다.
- `voku_usage_auditor`: 분석 요청 및 전달 이력만 읽는다. 분석 결과와 사용자 경로를 읽거나 기록을 수정하지 못한다.
- 두 역할은 비밀번호 없는 NOLOGIN 그룹이다. 현재는 기존 DB 관리자 `postgres`에만 역할을 부여한다. 웹앱 회원, 게시판 관리자, 운영자 Auth 계정, API의 anon/authenticated/service_role에는 부여하지 않는다. 별도 계정·공유 비밀번호를 자동 발급하지 않는다.
- 담당자를 추가할 때 DB 관리자가 개인별 전용 DB 로그인에 그룹을 부여한다. 앱 역할이나 다른 관리 역할을 함께 주지 않는다. 접근 종료 시 해당 그룹을 회수한다. 기존 Supabase SQL Editor/MCP는 `postgres`를 공유하므로 기록의 접속 주체가 사람별로 구분되지 않는다. 여러 분석 담당자가 사용할 때는 개인별 DB 로그인이 필요하다.
- 원본 데이터에 대한 읽기 전용 권한이다. 시스템은 조회 근거와 결과 발급 이력을 자동 기록하므로 PostgreSQL의 `READ ONLY` 트랜잭션 설정과는 다르다. DB 소유자·상위 관리자는 이 제한을 우회할 수 있으며, 이 역할은 DB 관리자 자체를 제어하는 장치가 아니다.

## 목적 기록 후 결과 받기

두 호출은 별도 트랜잭션이어야 한다. 첫 호출은 데이터 대신 요청 번호·행 수·결과 해시·만료 시각만 반환한다. 첫 기록이 커밋되기 전에는 결과를 읽을 수 없다. 결과를 받은 뒤 읽기 트랜잭션을 롤백해도 앞서 확정된 목적·범위·결과 해시 기록은 남는다.

Supabase SQL Editor에서 사용할 경우 **첫 블록을 실행하고 완료된 후** 반환된 요청 번호로 두 번째 블록을 실행한다. 아래 날짜는 실제 분석 기간으로 바꾼다.

```sql
-- 첫 실행: 조회 범위와 목적 기록. 한 번에 최대 31일, 최근 90일 이내.
set local role voku_usage_reader;
select voku_analysis.prepare(
  '2026-10-14'::date, '2026-10-14'::date,
  'archive_journey', '아카이브 탐색과 실제 열람 사이의 경로를 확인합니다', 'real'
);
```

```sql
-- 첫 실행이 끝난 후 별도로 실행. 발급된 requestId를 넣는다.
set local role voku_usage_reader;
select voku_analysis.read_result('발급된-requestId'::uuid);
```

허용 목적은 `archive_journey`(탐색·열람), `returning`(재방문), `participation`(후속 참여), `data_quality`(수집 품질), `incident`(오류 조사)다. 사유는 12~300자이고 이메일·URL·제어 문자는 거부한다. 사유에 이름·연락처·회원 번호를 적지 않는다. 목적의 실제 정당성은 담당자와 감사 담당자가 확인한다.

`real`은 테스트·관리자·봇·예시 활동을 제외한다. `test`와 `all`은 `data_quality` 또는 `incident` 목적에만 허용한다. 요청당 최대 5,000개 이벤트, DB 접속 주체당 시간당 20회이며 범위를 넘기면 명시적으로 잘림을 표시한다. 부분 경로로 전체 전환율이나 이탈률을 주장하지 않는다.

psql을 사용한다면 [실행 스크립트](../scripts/backend-analysis.sql)를 사용한다. 접속 정보는 사용자별 로컬 PGSERVICE/PGPASSFILE로 관리하고 저장소·브라우저·채팅에 넣지 않는다. 결과 파일이 필요하면 권한을 `umask 077`로 제한하고 Git에서 제외된 `artifacts/private/` 아래에 저장한다. 원시 경로 파일은 분석이 끝나면 삭제하며 외부 제출에는 사용하지 않는다. 서버의 자동 삭제는 다운로드한 파일까지 삭제하지 않는다.

## 결과에 남는 것과 제외하는 것

하나의 요청 안에서는 브라우저 번호로 여러 방문을 연결한다. 방문 순서·이벤트 순서·일자·방문 내 상대 초·화면 분류·공개 아카이브 회차와 쪽·열람 시간·작성 성공·유입/기기 범주·재방문 여부를 제공한다. 상대 시간의 기준은 선택된 범위 안에서 해당 방문의 첫 이벤트다.

번호는 요청마다 새로 만들어진다. 원래 브라우저/세션/이벤트 UUID, 회원/글/댓글 ID, 이메일, 닉네임, IP, 본문, 검색어, 정확한 시각, 내부 중복 확인 해시는 제공하지 않는다. 같은 브라우저만 연결하므로 기기 변경·브라우저 데이터 삭제는 다른 방문자로 잡힐 수 있다. 공개 자료의 선택·활동 날짜 등으로 정체를 추정할 여지는 남아 있으며 완전한 익명화를 보장하지 않는다.

기존 이벤트의 글·댓글 UUID도 비밀값을 섞은 해시로 전환하고 원래 컬럼을 제거한다. 앞으로는 수집 순간 실제 작성자·예시 여부를 검증한 뒤, 작성 중복 방지에 필요한 해시만 보관한다. 기존 작성 중복 방지와 집계 정의는 유지한다. 기존 백업·이전에 내려받은 원본은 이번 DB 변경만으로 소급 삭제되지 않으므로 백업 보관 정책을 함께 따른다.

`canonicalEvents`의 UTF-8 SHA-256이 `sha256`과 일치하는지 확인할 수 있다. 이것은 발급된 결과의 일관성을 확인하며 사람 수나 인과관계를 입증하는 인증은 아니다.

## 기록, 보관, 삭제

- 확정된 요청: 실제 DB 접속 주체, 사용 역할, 목적·사유, 조회 날짜·대상, 반환 건수·잘림 여부, 결과 체크섬, 발급/만료 시각. 사용자 경로·브라우저 번호는 감사 기록에 보관하지 않는다.
- 전달 이력: 결과 조회 시각과 요청 번호·접속 주체를 기록한다. 읽기 트랜잭션 롤백 시 테이블의 전달 행은 취소될 수 있으나, 이미 확정된 요청 기록은 남는다. 추가 `voku_analysis_delivery` PostgreSQL 로그는 트랜잭션 롤백과 별도로 남으며 외부 로그의 보관 기간은 Supabase 요금제/설정을 따른다.
- 임시 결과: 10분이 지나면 읽기 거부. 15분 주기 정리로 물리 삭제한다(정상 실행 시 생성 후 최대 약 25분). 작업 실패 시 읽기 만료는 계속 적용되지만 물리 정리는 지연될 수 있으므로 cron 실행 결과를 확인한다.
- 감사 기록: 365일 후 정리. 해당 정리 작업의 cron 실행 이력은 30일 보관한다. 상세 이벤트 90일·재방문 식별값 180일·집계 5년 정책은 유지한다.
- 브라우저 상세 기록 삭제: 해당 브라우저의 보관 중 이벤트와 식별값을 지우며, 그 브라우저가 포함된 임시 결과만 폐기한다. 기존 비밀값과 요청 번호로 요청별 브라우저 번호를 다시 계산해 포함 여부를 확인하므로 별도 대응표는 보관하지 않는다. 존재하지 않거나 이미 삭제한 브라우저의 반복 요청은 다른 임시 결과를 지우지 않는다. 감사 기록·결과 체크섬·비식별 집계는 유지한다.

```sql
set local role voku_usage_auditor;
select id, created_at, db_actor, db_role, purpose, reason,
       from_day, to_day, audience, row_count, truncated, sha256
from voku_analysis.requests order by created_at desc limit 100;
```

분석 스키마를 PostgREST 노출 목록에 추가하거나 앱 역할에 실행/테이블 권한을 부여하지 않는다. 결과 조회를 편하게 하려고 원시 SELECT 권한을 추가하면 목적 기록을 우회하게 된다.
